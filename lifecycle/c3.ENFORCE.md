# Enforce Stage

The Enforce stage ensures that approved standards become **lived practice** through deterministic, automated mechanisms.  
A standard that cannot be enforced mechanically is not a standard — it is a suggestion.

Enforce is where governance becomes real.

---

## Purpose

- Translate approved standards into **objective, automated enforcement**
- Remove ambiguity, interpretation drift, and manual policing
- Ensure consistent application across teams and systems
- Provide reference implementations that demonstrate correct usage

Enforcement is the bridge between governance intent and operational reality.

---

## Scope

Enforce applies to:

- CI rules and pipelines
- Linter configurations and static analysis
- Code scaffolds and templates
- Automated checks for UX, security, architecture, or process rules
- Reference implementations

If a rule is approved, it must be enforceable.

---

# Sub‑Stages

## E1. Enforcement Design

- Identify the enforcement mechanism(s)
- Determine the level of strictness (error, warning, block)
- Validate feasibility with SMEs and affected teams
- Ensure alignment with the approved specification

Outputs:
- Enforcement strategy
- Mapping of specification → enforcement rules

---

## E2. Implementation

- Implement CI rules, linters, templates, or scaffolds
- Create reference implementations
- Document enforcement behavior and configuration
- Validate correctness and determinism

Outputs:
- Working enforcement mechanisms
- Documentation for contributors

---

## E3. Validation

- Test enforcement across representative repositories
- Confirm no contradictions with the approved standard
- Ensure enforcement is deterministic and reproducible
- Validate that enforcement does not introduce regressions

Outputs:
- Validation report
- Steward approval to proceed to Adopt

---

# Required Artifacts

- Enforcement Specification  
- CI / Linter Rules  
- Templates / Scaffolds  
- Reference Implementations  
- Enforcement Documentation  
- Validation Report  

---

# Roles and Responsibilities

## Enforcement Engineer (Lead)

- Designs and implements enforcement mechanisms
- Ensures determinism and correctness
- Maintains enforcement as standards evolve

## Governance Steward (Verifier)

- Confirms enforcement matches the approved specification
- Rejects enforcement that contradicts or exceeds scope
- Ensures documentation and traceability

## Author (Support)

- Provides domain context
- Confirms enforcement reflects intended behavior

---

# Entry and Exit Criteria

## Entry Criteria

- Approved specification from Legitimize
- Enforcement Engineer assigned
- Steward confirms enforceability

## Exit Criteria

- Enforcement implemented and validated
- Documentation complete
- Steward approves transition to Adopt

---

# Quality Bar

Enforcement is complete when:

- Rules are deterministic and reproducible
- No manual interpretation is required
- Enforcement matches the approved specification exactly
- Reference implementations demonstrate correct usage
- Teams can adopt without guesswork

---

# Anti‑Patterns

- Manual enforcement (“just remind people”)
- Enforcement that contradicts the specification
- Overly strict rules that block legitimate use cases
- Enforcement without documentation
- Enforcement that varies across teams or repos

---

# Checklist for “Enforce Complete”

- [ ] Enforcement mechanisms implemented  
- [ ] Reference implementations created  
- [ ] Documentation published  
- [ ] Validation completed  
- [ ] Steward approval granted
